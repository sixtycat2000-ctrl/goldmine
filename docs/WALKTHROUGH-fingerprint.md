# 第二讲：指纹与身份模型 — 为什么一个字符串变了，全库就要重嵌

> 轮讲第二讲（2026-10-25）。代码主入口：`goldmine/fingerprints.py`（build/
> canonical/check/gate + embed_identity 系）+ `goldmine/backends/llama.py`
> 的 fingerprint_fields + 提取器注册表 EXTRACTOR_VERSIONS。读完应能答文末十问。

## 0. 一张图：身份其实是四层，不是一个数

```
第一层  嵌入指纹（fingerprint_json，v1 形状）
        八个规范字段 + 后端附加字段，canonical JSON 排序后 sha256[:16]
        → 管"向量家族不混"：search/增量 ingest 前过 gate，不符 exit 3
第二层  embed_id（v2 拆分，2026-10 起）
        指纹的子集——只有"决定存量向量取值"的字段
        → 管"哪些行要重嵌"：files.embed_id ≠ live 才重嵌
第三层  提取器版本注册表（EXTRACTOR_VERSIONS + current_extractors）
        每行的 extractor_version 在不在"本构建会写出的集合"里
        → 管"哪些行要重抽文本"：不在 = stale = 下次摄取重抽
第四层  评测基线身份（corpus_version + corpus_sha）
        → 管"评测分母没被偷换"：gate 对漂移响亮作废
```

人们说"指纹"时经常把四层混为一谈。分开之后，"改了 X 会发生什么"变成
查表题。

## 1. 第一层：指纹本体（管"拒绝服务"）

**build()** 收后端的 fingerprint_fields()，凑成八个规范字段：backend、
model_id、**model_sha256**、dim、prompts、pooling、normalization、
preprocessing，再并入后端附加键。**canonical()** 把它序列化成按键排序、
无空白的 JSON 字节——排序保证"键序不同 ≠ 身份不同"。**fingerprint_id**
= 这段字节的 sha256 前 16 位。

**媒体四件套是条件附加**：helper + mmproj 都能解析时才附加 media
（预处理串）、mmproj_sha256、media_budgets、media_routing。装了媒体能力
的机器和纯文本机器，指纹里有没有这四个键——**纯文本安装的指纹逐字节
不变**（有守卫测试钉死）。这就是为什么今天批次 B 改 MEDIA_PREPROCESSING
字符串（v4→v5）只影响装了媒体的机器。

**gate 在哪开火**：每次语义 search、每次增量 ingest——把库里存的
fingerprint_id 和 live 算的比。不同 → 抛 FingerprintMismatch → CLI
**exit 3**，错误信息里点名每个不同的键并给出修法（你亲手跑过：
docs/ANCHORS.md 第 2 条，differs in: media）。**词法检索不过这道门**——
它不碰向量，`--lexical` 永远可用，这是设计好的逃生门，不是降级凑合。

一个刻意的排除：**llama.cpp 构建串不在指纹里**。构建变了向量没变 →
不该惩罚用户重嵌。谁来证明"向量没变"？参考向量测试（ANCHORS 第 3 条）
——所以规矩是：构建/模型升级先跑参考向量，动了才升指纹字段。

## 2. 第二层：embed_id（管"哪些行重嵌"）

v1 指纹把四件独立的事捆成一个数（嵌入身份、分块、抽取语义、工具集），
后果是任何一件变都读成"全部重嵌"。v2 把**嵌入身份**单独拆出来
（fingerprints.py:150 起）：只有真正决定**存量向量取值**的字段进 embed_id
——backend/model/sha/dim/**prompts_doc**/pooling/normalization + 媒体
预处理串。

两个容易困惑的点：

- **查询提示词不进 embed_id，文档提示词进**。存量向量是文档侧算出来的，
  文档提示词变了 → 每个存量向量的取值变了 → 必须重嵌。查询提示词只影响
  查询那一个向量的算法，一个存量字节都不用动——所以 2026-10 的 v1→v2
  提示词重构对存量库是**零重嵌迁移**（迁移回填的 embed_id 与新库逐位相等，
  B2 绑定规则写死了这条）。
- **preprocessing（管道级）不进 embed_id**（它进第一层指纹）。管道整体
  语义变化由提取器版本层（第三层）负责逐行重抽，重抽自然重嵌。

## 3. 第三层：提取器版本注册表（管"哪些行重抽"）

每行文件存一个 `extractor_version` 字符串（如 `pdftotext@24.08.0`、
`media-ffmpeg-mm.v3`、`pdftotext+arocr+visionocr@24.08.0`）。
`current_extractors()` 给出**本构建可能写出的全部字符串集合**。行的版本
不在集合里 = stale = 下次摄取重抽。关键设计：**方向永远朝安全**——
注册表漏登记一个新串，后果只是"多抽一遍"（无害）；反之（行为变了版本
没变）才是灾难（旧行静默过期）。所以登记新行为时必须"行为变 → 版本串
变 → 注册新串"三件套。

这层的两个真陷阱（都被踩过、都有测试钉死）：

1. **字面量漂移**：extraction.py 曾三处硬编码 "media-ffmpeg-mm.v2"，注册表
   升 v3 而代码没跟上 → 写出的串永不在注册表 → **每行永久反复重抽**
   （2026-10-25 批次 B 评审抓的 D1）。修法：单一共享常量 + 相等性测试。
2. **组合爆炸**：一个文件可能叠加多种升级（thin 页 OCR + 阿拉伯页替换）
   → 版本串由统一的组装函数拼（`upgraded_pdftotext_version`，按字母序），
   注册表登记全部四种组合——组装函数和注册表必须同源。

还有一类"升级路径"不走版本表：**redo 标记**（如 OCR 从不可用变可用：
`_needs_ocr_redo` 看 states 里的 unavailable/error）。语义是"当时没能力、
现在有能力了，补一次"——终态后不再触发，不 churn。

## 4. 第四层：评测基线身份（管"分母不被偷换"）

评测 gate 的基线文件带 corpus_version + corpus_sha。语料清单变了 →
gate 响亮作废（不是静默拿旧分母比新语料）。重生的唯一通道是审计门：
备份 → 重建 → 逐条对账差异（预期内的放行、未解释的漂移追责）——
今天批次 B 的 eval-rebuild-audit.md 就是现场范例：8 项差异每一项都有
归属，其中"+1 文件"查实是新命令文件落进了摄取根，不是夹带。

## 5. 腐烂风险清单（维护者要盯的地方）

1. **新行为三件套**：改任何提取/嵌入行为时，版本串和注册表必须同步——
   最常见的遗漏是"行为变了、串没变"（静默过期，最危险方向）。
2. **共享常量与注册表同源**：任何版本字面量出现第二处，就要么合并、
   要么加相等性测试（现有 media 钉子是样板）。
3. **媒体 extras 的条件性**：动 llama.py 的 fingerprint_fields 时保住
   "纯文本安装逐字节不变"——守卫测试在，但别绕过它加字段。
4. **审计门纪律**：基线重生必须先备份、后逐条对账；"顺手重建"就是
   夹带的入口。
5. **升级 llama.cpp/模型**：先跑参考向量（ANCHORS 第 3 条），动了才升
   指纹字段——别反过来。
