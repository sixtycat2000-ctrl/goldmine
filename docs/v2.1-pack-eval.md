## 1. R2 — `--context N` (neighbor expansion)

### 1.1 Neighbor definition

Neighbors of hit chunk `H` = the file's **renderable text segments** immediately before and
after `H` in position order. Precisely:

- Candidate set: all segments of the same `files.id` with `kind != 'name'` that have an FTS
  row (they have text to show). The `name` stub and text-less vector rows (pure image
  vectors) never appear as neighbors — they have nothing to expand.
- Order: `(loc, loc_end, id)` ascending. For docs/code this is line order; for pdf, page
  order; for audio/video, `loc` is seconds, so neighbors are the adjacent time windows —
  no special case needed.
- Selection: `N` before + `N` after `H` (not cascading — neighbors of neighbors are not
  taken). A start-of-file / end-of-file hit simply has fewer sides.
- A **name-segment hit** (metadata-only file, or a hit on the filename stub) gets NO
  expansion; rendered with the note `context: name hit` (honest: there is nothing around
  it). Same for a hit whose segment has no FTS row.

### 1.2 CLI surface

```
goldmine search <query> --context N
```

- One flag, `--context N`, `N ≥ 0`. `N > 3` clamps to 3 with a stderr notice
  (`--context 7 clamped to 3`); `N < 0` is a usage error (exit 2). Default: `0` for human
  list output and `--json`; **`1` in pack mode** (explicit `--context 0` opts out there
  too). Justification: ROADMAP R2 fixes the pack default ("打包模式默认带 1 层邻块");
  list mode is navigation where excerpts suffice — printing 3 chunks × 20 hits makes the
  list unreadable and was never the ask.
- 3-clamp cost bound: ≤ 7 chunks ≈ 3150 tokens per record — a record can never exceed a
  4000-token budget by more than the slim-fallback margin.

### 1.3 Effect per output mode

- **Human list**: under each hit, one note line — no neighbor text:
  `   · context: before L283-313 · after L350-378 (+2 chunks)`
  (loc formatting reuses `_render_loc`; sides listed only when present).
- **`--json`**: each hit gains `"context": [{"role": "before|after", "loc", "loc_end",
  "text"}, ...]` (full texts) and, when expansion was impossible, `"context_note":
  "name hit"`. Additive keys only; absent when `--context 0` or no neighbors — the v2
  search --json contract is otherwise unchanged.
- **Pack**: neighbors merge into the record text (§2.3).

### 1.4 Merged-record semantics (hit + neighbors, one record)

A record exists because of its hit. Rules:

1. Parts render in position order (before-context, hit, after-context) so reading order
   matches the document. The record header's `loc/loc_end` and score stay the **hit's** —
   the authoritative pointer to what matched.
2. If a neighbor segment of record R is itself a later hit H₂, H₂ does NOT get its own
   record (its text is already in R). R's header gains `· also match [k] score X.XX L..`
   (k = H₂'s rank); `--json` records it in `"also_hits"`; the sources footer lists it as
   ` + hit[k]`. The earlier (higher-ranked) record always absorbs the later one.
3. Cross-record dedup: a segment renders at most ONCE per pack. If a segment would appear
   as neighbor of record 3 after appearing in record 1, it is skipped (its slot is not
   backfilled by extending further — simpler and keeps positions contiguous).

### 1.5 Seam dedup (the 48-token overlap), precisely

Chunker semantics (verified in `chunker.py:_walk_tokens`): on a NON-paragraph cut the next
chunk rewinds `overlap` (48) tokens, so consecutive chunks share that span; both chunks are
`.strip()`ed slices of the same cleaned text, so the shared span is byte-identical in both.
Paragraph cuts and code chunks carry NO overlap. The seam is mid-line (token boundary), so
**line-based dedup would miss it**; dedup is char-aligned:

> When appending chunk Y after chunk X in the same record, if their line ranges overlap or
> touch (`Y.loc ≤ X.loc_end`), find the largest `C ∈ [24, 640]` with
> `X.text[-C:] == Y.text[:C]`; if found, drop `Y`'s first `C` chars; else keep `Y` whole.

- Floor 24: a real 48-token overlap is ≥ 48 chars in any script; anything shorter is
  coincidence and dropping it would eat real content. Under-trimming (a missed overlap ≤
  640 duplicated chars) is safe and preferred over any over-trim risk.
- Cap 640 chars: comfortably above the worst realistic 48-token overlap (URL-heavy text);
  a longer duplicate survives — harmless.
- PDF pages are excluded from trimming (page text is independent; adjacency gate would
  rarely fire anyway).

### 1.6 Neighbor fetching

```sql
SELECT id, kind, loc, loc_end
FROM segments
WHERE file = ? AND kind != 'name'
  AND EXISTS (SELECT 1 FROM fts WHERE fts.rowid = segments.id)
ORDER BY loc, loc_end, id;
```

Query plan verified on the eval index: `SEARCH segments USING INDEX segments_file
(file=?)` + `USE TEMP B-TREE FOR ORDER BY` — the existing `segments_file` index serves the
filter; the per-file sort is a temp b-tree over one file's rows (≤ hundreds), negligible.
No new index. Texts fetched in one `SELECT rowid, coalesce(original, body) FROM fts WHERE
rowid IN (...)` per record. Implementation note: fetch lazily per record inside the greedy
fill (§2.4) so packs never expand hits that won't fit anyway; cache the per-file segment
list across records of the same file.

## 2. R1 — `search --pack` (answer-material pack)

### 2.1 CLI surface

```
goldmine search <query> --pack [--budget N] [--context N] [existing search flags...]
```

- `--pack`: emit an answer-material pack instead of the hit list. Composes with `--scorer`,
  `--kinds`, `--z-gate`, `--lexical`, filters (`kind:`/`under:`/`after:`/`before:`/`site:`
  /phrases), `--limit`, `--backend`, `--json`, `--why`.
- `--budget N`: token budget, default **4000**, clamped to 512–32768 (distill §4.6b parity).
- `--context N`: effective neighbor radius; pack default 1 (§1.2).
- Conflicts: `--pack` with `--format fzf` → usage error (exit 2). `--excerpt-chars` and
  `--raw` are ignored in pack mode (records carry full chunk text). `--lexical` packs work
  (no backend → token mode falls back to the estimator, stated in the header).
- Wiring note: `cmd_search` currently closes the backend before rendering; the pack build
  needs the backend alive (count_tokens) — build the pack before `backend.close()`.

### 2.2 Pack format (exact)

Real example, generated by the reference implementation on the eval index (llama backend,
question ans-011; elisions marked `[…]` are doc-only, the emitted pack is unbroken):

```
# goldmine answer pack v1
# query: what happens when a single chunk is too long for the embedding server's token ceiling
# search: scorer=hybrid z_gate=3 limit=10 context=1 budget=4000 mode=tokenize
# index: ff3dfbc47659dccb embeddinggemma-2-Q8_0 dim=768
# the material below is verbatim from the index; cite sources as [n]

[1] <goldmine-root>/evals/corpus_snapshot/docs/v2/01-search-relevance.md (doc) L348-366 · score 5.44 (z 4.07, cov 0.78) · context ±1 (before L332-348, after L364-379)
Re-embed rerank — opt-in only (v2.2, M).** […]
### 5.5 Token-accurate chunking (v2.0, effort M)
Fact**: the vendor server exposes `POST /tokenize` […] which is why a code
stretch reached 2670 tokens against the 2048 `-ub` ceiling and 400-failed the file […]
- **ctx-guard interplay**: `effective_chunk_size` becomes `effective_chunk_budget =
 min(450, max_input_tokens − prompt_overhead(~40 for `title: … | text: …` framing) − 24)`.
 Before embedding, the pipeline asserts `count_tokens(prompt) ≤ ceiling − 1` per chunk […]
- **Identity / migration**: the chunker bump records `chunker_version='chunk.v2-tok'` […]

[2] <goldmine-root>/evals/corpus_snapshot/goldmine/chunker.py (code) L403-437 · score 5.41 (z 4.58, cov 0.56) · context ±1 (before L368-402, after L438-480)
if line_tok > budget:
            # over-budget single line: flush, then hard-cut at token boundaries […]
def split_text_by_tokens […] the SPLIT-not-fail backstop for anything that still exceeds the ceiling. […]

# sources
# [1] <goldmine-root>/evals/corpus_snapshot/docs/v2/01-search-relevance.md L332-379
# [2] <goldmine-root>/evals/corpus_snapshot/goldmine/chunker.py L368-480
# pack: 2 records · 10 hits · 0 duplicates folded · 8 skipped (budget) · used 2902/4000 tokens (tokenize)
```

Grammar:

- **Header** (4 `#` lines + guidance line): version tag; the clean query (post
  filter-parse, as searched); the search settings incl. token mode (`tokenize` when
  `count_tokens` is available, else `estimate` — decided by ONE probe call before
  selection, so the header can print it); the index fingerprint line
  (`fingerprint_id model_id dim=…`); the verbatim-material guidance line for the consumer.
- **Record**: one `[n]` header line, then the merged verbatim text (blank-line-terminated).
  Header fields, in order: `path (kind) LOC · score S.SS (z Z.ZZ, cov C.CC)` — z omitted
  when None (vectorless) — then optional ` · context ±N (before …, after …)`, then one
  ` · also match [k] score …` per folded hit. `LOC` renders via `_render_loc`
  (`L314-349` / `p.4` / `12s-35s`).
- **Footer**: `# sources` + one line per record (record n → path + span covered by its
  parts, i.e. first-part loc to last-part loc, plus ` + hit[k]` markers), then the
  manifest line: records / hits / duplicates folded / skipped-over-budget / used-vs-budget
  with the token mode. The `used N` figure is a render-measure fixpoint (render with N,
  measure, repeat until the printed number equals the measured one — converges ≤ 3 rounds;
  if the fixpoint itself overshoots budget, drop the last record and redo).

Known cosmetic risk, accepted and documented: a chunk whose text begins a line with
`[word]` can pattern-match the `[n]` record header to a naive parser. The pack is built to
be PASTED for an LLM, not machine-parsed; machine consumers use `--pack --json`.

### 2.3 Budget accounting

- **What counts**: the ENTIRE stdout byte string — header, every record line (headers +
  text), sources footer. Justification: the completion standard is "输出不超过 4000
  token 的材料包"; the consumer pastes the whole thing; header+footer are ~1–3% overhead
  and deterministic, so whole-output accounting costs ~2 records' worth of nothing and
  makes the claim self-verifiable (`count_tokens(stdout) ≤ budget` holds by construction
  and is testable).
- **How measured**: `EmbeddingBackend.count_tokens([pack_text])` — ONE text per call
  (`/tokenize` cannot batch; per call ~5–10 ms). A pack costs ≤ ~4 greedy iterations ×
  ≤ 3 fixpoint renders ≈ a dozen calls ≈ ~100 ms. Estimator fallback (`est_tokens`,
  chars/4) when the backend has no `count_tokens`; the mode is printed in the header.
- **Policy (revised 2026-10-22)**: accept fitting whole primary seeds in rank
  order before any optional expansion. A nonfitting seed is skipped and later seeds
  may still fit. Then attempt the first support slot across accepted records, then
  their second support slot, then neighbors by distance/rank/source order. Ordinary
  neighbor distance is renderable-segment ordinal distance; PDF distance is actual
  page difference under the existing page-membership rule. Never truncate text or
  citations. Optional expansion failure leaves the fitting seed intact and does not
  count as a skipped hit. No fitting seed yields a genuinely measured empty pack;
  if its complete required envelope cannot fit, return `budget_too_small`.

### 2.4 Selection, ordering, ties

- Pure `scorer=semantic` ablation retains its existing fallback primary and an
  empty supporting tuple; only requested neighbors may expand it. The protected
  semantic-support policy applies to hybrid/default, preserving the historical
  single-channel ablation and fixed capacity workload. No source-specific exception.
- Candidate pool = the search hits under the existing flags. Consider the first 24
  **hit attempts**, with later hits counted as record-limit skips. This deliberately
  replaces the historical cap of 24 emitted records after folding: many duplicate
  hits may produce a different cap count. No new numeric knob or quality profile.
- Keep an accepted seed/expansion ledger. Freshly derive records, parts, numbering,
  source associations, citations and all counts after every rollback. A deleted
  seed must not leave an `also hit`, path or citation ID in a survivor.
- Final duplicate folding requires identical complete emitted material and a
  representable primary-only secondary. `also match` requires every accepted part
  of the secondary to be represented by actual stored IDs **and complete literal
  text** in an earlier record. SID membership across a trimmed seam is insufficient.
  A secondary with a new support/neighbor remains a complete record. No approximate
  or cosine-based fold; retain each real source citation. Do not refill space
  freed by final folding.
- Output order remains search rank order, with consecutive pack record numbers.
  File ranking/scores stay unchanged. Header scores are file scores, not a claim
  about a selected segment's semantic score or answerability.
- Every candidate part is stored text. Keep disjoint page/time/line evidence
  labelled separately and retain all contributing citations. A name record stays
  stored metadata with null body position; a vector-only record is explicit about
  having no quotable text.
- The full envelope is measured in one token mode. Tokenizer loss restarts the
  allocation once in estimate mode. Each fixpoint uses at most four counts; final
  rollback removes one accepted addition per step. Failed convergence/overflow
  never returns an unmeasured or oversized context.

### 2.5 Determinism contract

Same index + query + flags ⇒ **byte-identical** stdout. Required behaviors (all verified
in the reference implementation, 20/20 byte-identical re-emits):

- No timestamps, no wall-clock, no durations anywhere in the pack (header/footer carry
  only settings, fingerprints and counts). Run metadata goes to the sidecar JSON / eval
  run records only.
- Fixed orderings everywhere (rank order; parts by position; sources by record).
- Floats formatted with fixed precision (`score %.2f`, z `%.2f`, cov `%.2f`).
- `--pack --json` is deterministic too (same rule) — it is the machine form of the same
  pack: `{"schema": "goldmine.pack/v1", "query", "settings": {...}, "index": {...},
  "records": [{"n", "path", "kind", "loc", "loc_end", "score", "z", "cosine",
  "coverage", "why?", "context": [{"role", "loc", "loc_end"}], "also_hits": [...],
  "text", "tokens"}], "duplicates_folded", "skipped_over_budget", "used_tokens",
  "token_mode"}`.

### 2.6 Edge cases

- Zero hits: header + no records + `# pack: 0 records · 0 hits · …` footer, exit 0.
  The eval's traps rely on the answerer refusing on such material.
- A record's text can contain lines starting with `#` or `[` — accepted (§2.2).
- `--lexical` pack: allowed, `mode=estimate`, no fingerprint gate (same as search).

## 3. R4 — answer eval (materials → AI answering → grade)

### 3.1 Hard constraint and the 3-phase protocol

The repo script CANNOT call GLM (no API in the repo). The judge runs as ZCode subagents
spawned by the human/orchestrator. The protocol therefore orchestrates ON DISK:

```
evals/answer/
  questions.jsonl          # committed question set (§3.2) — the only repo-tracked input
  answerer_prompt.md       # committed verbatim prompt (§3.3) — paste-stable
  grader_prompt.md         # committed verbatim prompt (§3.4)
  packs/<qid>.md           # Phase A output: the pack (paste material)
  packs/<qid>.json         # sidecar: fingerprints, hits, settings, used tokens
  lists/<qid>.md           # Phase A --arm list: plain search-render comparison material
  answers/<qid>.md         # Phase B output: the answerer's reply
  grades/<qid>.json        # Phase C output: checks[], score, reason, shas
  answer_baseline.json     # committed baseline (evals/answer_baseline.json)
```

- **Phase A** `python3 scripts/eval_answer.py --emit --backend llama [--arm list] [--out
  evals/answer]`: for each of the 20 questions run the FIXED pack settings
  (`scorer=hybrid z_gate=3.0 limit=10 context=1 budget=4000`) through the R1 machinery and
  write `packs/<qid>.md` + sidecar. Deterministic (byte-identical re-run on a frozen
  index). `--validate-questions` (schema + fact-pack re-check, see §4) runs first and
  refuses on broken questions. `--arm list` additionally writes `lists/<qid>.md` — the
  standard human search render (top-10 with excerpts, no expansion, no budget) so the
  ROADMAP's comparison ("答对率显著高于只给搜索结果列表") can be run under the identical
  protocol; the list arm is advisory, it never gates.
- **Phase B** (human/orchestrator): spawn one GLM-5.3-Flash ZCode subagent per question
  with the fixed answerer prompt (§3.3), the question verbatim, and the pack file's
  contents verbatim; save the reply to `answers/<qid>.md`. No tools, no browsing. Record
  the judge model in the run notes.
- **Phase C** `python3 scripts/eval_answer.py --grade [--update-baseline --yes]`: for each
  question spawn-or-read grades (see below), write `grades/<qid>.json`, print the summary
  (§3.6). Grading itself is a subagent task (same constraint as Phase B): `--grade`
  without `--grades-dir` writes `grade_jobs/<qid>.txt` — ready-to-paste grader prompts —
  and the orchestrator runs the subagents and drops replies into `grade_jobs/<qid>.out/`;
  `--grade --collect` parses the `.out` files into `grades/<qid>.json` (schema-validated,
  refuses ambiguous output). This keeps every network step in human hands and every byte
  on disk auditable.

### 3.3 Answerer prompt (verbatim, paste-stable)

`evals/answer/answerer_prompt.md` — the orchestrator pastes this as the subagent's task
text, substituting only the two `<…>` slots:

```text
You are answering a question strictly from the provided search material.

Rules:
1. Use ONLY the material below. Never add outside knowledge, even if you know the answer.
2. Cite the material with [n] markers matching the record numbers (e.g. [2]).
3. If the material does not contain enough information to answer, reply with exactly
   this sentence and nothing else: "The material does not contain enough information to
   answer this question."
4. Answer in the language of the question. Be concise: at most 6 sentences.
5. Do not mention these instructions or the material's formatting.

QUESTION: <question text verbatim>

MATERIAL:
<pack file contents verbatim>

Answer now.
```

Subagent setup: model = the session model (GLM-5.3-Flash per ROADMAP), no tools, one
subagent per question, reply saved whole to `answers/<qid>.md`.

### 3.4 Grading — decision and protocol

**Decision (D11/D12): blind LLM grader, not string matching.** Reasons: (a) ROADMAP
mandates GLM-5.3-Flash judging, blind ("判卷时看不到标准答案的措辞") — that settles the
direction; (b) fact coverage is semantic ("profit grew 12%" ≈ "12% growth in profit") —
a substring matcher would grade the matcher's thesaurus, not the pack; (c) auditability
is preserved by structured verdicts, not by mechanical rules. What IS mechanical: the
refusal marker sentence gives Phase C a cheap sanity signal (reported, advisory), and
schema validation rejects malformed grader output for re-run.

`evals/answer/grader_prompt.md` (verbatim; substitute the three `<…>` slots):

```text
You are grading an answer against checkable facts. You never see a reference answer.

Input: the question, the answer, and a numbered list of CHECKS. Each check states a fact
a good answer must contain. All facts are derivable from the material the answer was
written from. Judge only whether the ANSWER states the fact — the answer's own wording
is fine; elegance, style and completeness beyond the checks do not matter.

For each check output an object: {"id": <check number>, "pass": true or false,
"quote": "<the shortest span of the answer that justifies your verdict, or \"\" if none>"}.

Then choose "score":
- Answerable question (checks are fact checks): score 2 if EVERY check passes AND the
  answer cites at least one [n] marker; score 1 if at least half the checks pass; else 0.
- Trap question (the check list starts with the word TRAP): score 2 if the answer clearly
  states the material does not cover the question (or an equivalent honest refusal) and
  does NOT assert an answer; score 1 if it refuses but still guesses; score 0 if it
  asserts an answer as fact.

Also output "reason": one short sentence.

Output ONLY this JSON object, nothing around it:
{"checks": [{"id": 1, "pass": true, "quote": "…"}, …], "score": 0, "reason": "…"}

QUESTION: <question text verbatim>

CHECKS:
<for answerable: the must_facts, numbered, verbatim>
<for traps: "TRAP — the material is known not to cover this question." followed by the
 must_facts phrased as refusal checks, e.g. "The answer states that the material does
 not explain any CSV export (or equivalent honest refusal).">

ANSWER:
<answers/<qid>.md contents verbatim>

Grade now.
```

Grader setup: GLM-5.3-Flash subagent, no tools, blind (the prompt structurally excludes
golden text — `must_facts` only). Output parsed into:

```json
{"qid": "ans-011", "score": 2,
 "checks": [{"id": 1, "pass": true, "quote": "…"}],
 "reason": "…",
 "answer_sha256": "…", "grader_prompt_sha256": "…",
 "graded_at": "2026-10-18T…", "judge_model": "GLM-5.3-Flash (ZCode subagent)"}
```

`graded_at`/`judge_model` live in the grade file only — audit metadata, never in pack
bytes. A re-grade is a fresh subagent run over the same stored inputs; any dispute
resolves by reading `checks[].quote` against `answers/<qid>.md`.

### 3.5 Baseline + gate

`evals/answer_baseline.json` (committed, `--update-baseline --yes` only, mirroring
`eval_real.py` discipline):

```json
{"schema": 1,
 "protocol_version": "answer-eval/v1",
 "date": "2026-10-18",
 "judge_model": "GLM-5.3-Flash (ZCode subagent)",
 "pack_settings": {"scorer": "hybrid", "z_gate": 3.0, "limit": 10, "context": 1, "budget": 4000},
 "index": {"fingerprint_id": "…", "model_id": "…", "model_sha256": "…", "dim": 768,
           "chunker_version": "chunk.v2-tok"},
 "questions_sha256": "…", "prompt_versions": {"answerer": "answerer.v1", "grader": "grader.v1"},
 "corpus_version": "v2-2026-10-17",
 "mean_score": 0.0, "answered_rate": {"value": 0.0, "n": 16},
 "honest_refusal_rate": {"value": 0.0, "n": 4},
 "per_question": {"ans-001": {"score": 2, "answer_sha256": "…"}, …},
 "per_class": {"single": …, "multi": …, "cross": …, "trap": …},
 "list_arm": null,
 "gate": {"threshold": 0.1, "rule": "mean score drop > 0.1 vs baseline -> exit 1", "n": 20, "atom": 0.05}}
```

**Gate** (`scripts/eval_answer.py --gate`, compares the CURRENT grades dir against the
baseline): mean score drop `> 0.1` → print the failing questions + exit 1; otherwise a
green line. Threshold math (n=20, scores 0/1/2): one answerable question contributes
score/20, so one atom (a 2→1 or 1→0 waver) = 0.05, a full miss (2→0) = 0.1. Strictly
greater than 0.1 means tripping requires ≥ 3 atom flips, or a full miss plus another
atom — a single grader waver cannot trip, and even one full miss sits at (not past) the
wire, which is right for borderline questions where grader noise concentrates. Real
material damage (a ranking change that starves several packs) moves multiple questions
at once and clears the bar comfortably.

**Invalidation check** (runs BEFORE any comparison; any mismatch → exit 2 with the
mismatch list and `re-run Phase B deliberately, then --update-baseline --yes`, never a
cross-fingerprint comparison): `index.fingerprint_id`, `index.model_sha256`,
`index.chunker_version` (a chunker bump re-cuts every chunk — all locs and pack texts
change), every key of `pack_settings`, `questions_sha256`, `prompt_versions`,
`corpus_version`, `judge_model`. These are exactly "ranking-affecting or
answer-affecting" changes; the baseline's answer shas additionally pin WHICH answer run
the scores describe.

### 3.6 Statistics honesty (house style)

- Every run prints: mean score; answered-rate (non-trap score ≥ 1) with exact
  Clopper-Pearson 95% CI (reuse `eval_real.binom_ci`); honest-refusal-rate (trap score 2)
  with the same; per-class means labeled **advisory** (n = 4–6 ≪ 20); percentile
  bootstrap CI on the mean (seeded, reuse `eval_real.bootstrap_ci`).
- Standing label on every metric line until a baseline exists: `advisory-until-baseline`.
- n=20 → 1 question = 0.05 — printed verbatim in the summary header, same convention as
  `eval_real`'s per-tag notes.

## 6. Risks

1. **Judge noise** (LLM grading is nondeterministic run-to-run): fixed prompts, structured
   verdicts, stored grades, and the >0.1 threshold (≥3 atoms) bound the damage; a
   one-off double-grade variance measurement is the first baseline run's side note.
2. **Trap leakage via corpus growth**: `--emit --check-facts` re-validates absence
   patterns on every emit (warning, not error; traps re-reviewed at re-baseline).
3. **Seam under-trim** on >640-char overlaps (URL-dense code): duplicates survive —
   wasted budget, never lost content. Accepted.
4. **Pack budget tightness** (3 expanded records at 4000): enough for the validated
   question set; users raise `--budget` freely; Phase A settings are pinned and
   fingerprinted, so experiments never contaminate the gate.
5. **Grader availability**: grading is human-orchestrated; the protocol degrades to
   "grades arrive late", never to silent score drift (shas pin everything).
6. **Corpus drift**: same answer as `eval_real --gate` — snapshot-pinned manifest,
   `corpus_sha` verified before any comparison.

### 7.2 F2 — gate variance (P1)

A `mean-drop > 0.1` gate trips at Bin(20, q) ≥ 3 — a 5% per-question waver already gives
a 7.5% false-trip rate, 10% gives 32%. Therefore:

- `--update-baseline --yes` REQUIRES the variance data first: a second independent Phase B
  round (`answers2/<qid>.md`, all 20, same model — `answers/run.json` records the answerer
  id) and double-grades (`grades2/`, ≥ 12 questions, covering EVERY round-1 score-1
  question).
- The baseline stores the measured `variance`: `answerer_flip_rate` (sha disagreement
  across rounds / 20) and `grader_flip_rate` (score disagreement on the double-graded set).
- The gate threshold is DERIVED: q_eff = 1−(1−p_a)(1−p_g); smallest t in
  {0.10, 0.15, 0.20, 0.25, 0.30} whose no-change trip probability
  P(Bin(16, q_eff) ≥ ceil-atoms) stays under 5%. 0.1 is kept only if the measured rates
  clear that bar; otherwise the threshold raises.
- `--gate` refuses the comparison when MORE THAN 2 answer files' shas differ from the
  baseline's recorded answer shas (deliberate re-run + re-baseline forced). ≤ 2 drifts
  are printed and allowed (a single re-answer must not invalidate a whole baseline).

### 7.3 F3 — model pinning (P1)

The baseline gains `models: {answerer, judge}` (ZCode GLM-5.3-Flash identifiers, recorded
as strings) and BOTH join the invalidation set (§3.5). Wording fix: §3.1 Phase B records

`pack_settings` gains `token_mode` (recorded from the emit sidecar; compared in the
invalidation set).
