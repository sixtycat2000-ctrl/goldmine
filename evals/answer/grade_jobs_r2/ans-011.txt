QUESTION: what happens when a single chunk is too long for the embedding server's token ceiling

(no extra note for this question)

CHECKS:
1. An 1800-char code stretch once measured 2670 tokens against the 2048 ceiling and 400-failed its file (the incident that drove the fix)
2. The chunk budget shrinks to min(450, max_input_tokens - prompt framing (~40 tokens) - 24 slack)
3. A single over-budget stretch is hard-cut at a token boundary (split-not-fail) instead of failing the file
4. Before embedding, the ctx guard counts tokens and splits any still-oversized chunk

ANSWER:
When a chunk would exceed the server's token ceiling, the pipeline asserts `count_tokens(prompt) ≤ ceiling − 1` per chunk before embedding, and on violation it splits that chunk at a token boundary and continues — making the old failure mode structurally impossible instead of a per-file `failed` [1]. This replaces the v1 behavior, where a `len // 4` estimate let a code stretch reach 2670 tokens against the 2048 `-ub` ceiling and 400-fail the whole file [1]. As a backstop, `split_text_by_tokens` hard-splits anything that still exceeds the ceiling into pieces of at most `max_tokens` tokens each, cut at token boundaries when a tokenizer is available (proportional char cuts otherwise) — a "SPLIT-not-fail" guard [2]. The per-input budget itself is computed as `min(450, ceiling − framing(~40) − slack(24))`, flooring at 64 tokens [2].
