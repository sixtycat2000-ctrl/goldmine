QUESTION: how are code chunks cut differently from prose chunks

(no extra note for this question)

CHECKS:
1. Code chunks align to whole lines, accumulating lines up to the token budget
2. A single line longer than the budget becomes its own chunk, hard-cut at token boundaries
3. The estimator converts the token budget with the measured code density (CODE_CHARS_PER_TOKEN) so code stretches are sized correctly
4. Prose cuts prefer paragraph/sentence/whitespace boundaries; code has no such preference

ANSWER:
Prose chunks are cut by tiered candidate boundaries — paragraph first, then sentence, then whitespace — each searched within the window at least half the budget deep, falling back to a hard cut at the budget's token boundary; paragraph cuts carry no overlap while other cuts back up ~`overlap_tokens` tokens [1]. Code chunks instead accumulate whole lines up to the same token budget, so cuts land on line boundaries rather than sentence or paragraph boundaries [2]. A single over-budget line in code is hard-cut at token boundaries, a rule adopted after v1's whole-line-own-chunk behavior shipped an 82929-token single-line JSON blob as one chunk against the 2048 ceiling [1][2]. Paragraph-style overlap therefore does not apply to code — over-budget lines are simply split at token edges [1]. When no real tokenizer is available, the fallback also differs: prose converts the budget with a generic chars-per-token estimate, while code uses a measured code density (`CODE_CHARS_PER_TOKEN`) [1][2].
